# M5B — PO-approved product and architecture policy (2026-10-29)

**Authority:** Product Owner explicitly approved the discussed P1–P10 policy package in the Tarif Atlası project conversation on 2026-10-29. Record under DEC-022. **Status: PO_POLICY_ACCEPTED / PLANNED / NOT IMPLEMENTED / NOT AUTHORIZED TO CODE.** No approval to merge, tag, publish or access the PO's normal local profile. Parent planning issue: [#14](https://github.com/fatihemres/personal-recipe-library/issues/14). This is a design contract, not a claim that tables, IPC, migrations, UI or tests already exist.

## Accepted user-facing behavior (P1–P10)

1. **P1 — Capture boundaries.** Immutable committed-content versions on initial successful recipe creation, subsequent *meaningfully changed* explicit recipe saves, and restore. A no-op Save, pending edits, draft autosave/recovery, favorites, ratings, collections, archive/trash and their reversals do not create a content version. Distinguish a content version number from the existing `recipes.revision` optimistic concurrency counter (which also increments on lifecycle changes).
2. **P2 — Restore semantics.** A historical version is read-only. Restore keeps the existing recipe ID and all older snapshots; it creates a *new* current version and recipe revision, annotated with the restored-from version. Confirm before replacing the current committed content. Never discard or overwrite an active draft silently; reject stale `expected_revision`/draft conflicts. No mutation if required historical references cannot be resolved safely.
3. **P3 — Retention.** No automatic pruning, age limit or last-N cap for committed history. Measure and paginate local history. A deliberate permanent recipe purge may remove its owned history **only with explicit confirmation and reference-safety checks**. This does not authorize per-version deletion, automatic garbage collection of still-referenced assets, or an irreversible purge bypass.
4. **P4 — Legacy installation.** On a safe forward-only upgrade, create exactly one baseline snapshot of the *currently persisted* aggregate per preexisting recipe. Label it as an upgrade baseline, not an authentic first-created/earlier historical revision. Preserve original recipe IDs, order, typed steps, drafts, exact quantity text, catalog identities and independent M4B metadata. Empty and old profiles must both work; do not fabricate earlier versions.
5. **P5 — Variations.** A variation is an independent recipe with its own UUID, committed snapshots and edits. It can have at most one direct parent and may have multiple children; variation chains are allowed, cycles/self-parentage are not. Creating a variation copies the selected current recipe's content into its own initial version; it does not copy the entire source version history. Neither side auto-synchronizes when the other changes.
6. **P6 — Related recipes.** Explicit symmetric recipe-to-recipe relationships, visible from both recipes, independent of variations and without implied recipe merging, ingredient sharing or combined execution. Reject self-links and duplicate symmetric pairs. Relationships are managed separately from committed content version capture, with explicit lifecycle rules.
7. **P7 — Substitutions.** Explicit recipe-specific alternatives attach to an **ingredient line ID** in that recipe, not an ingredient's global catalog identity. Alternative quantities/units are optional and only user-authored; no invented g/mL equivalence, conversion, ABV, nutrition or automatic primary-line replacement. Selecting an alternative does not edit the authoritative recipe until the user deliberately changes/saves that line (which creates a committed version). Warn on line removal; preserve historical substitution data in later snapshot formats when this slice ships.
8. **P8 — Lifecycle/purge.** Archive and trash preserve version history, relations, independent variations and owned content. Permanent purge of a referenced parent must **block by default**, present dependent relationships, and require deliberate acknowledgement before detaching live references; child recipes and their own histories remain untouched. No cascading deletion of independent recipes. A purge must safely account for historical ingredients, snapshot references, future media and active drafts. Do not silently replace missing ingredient IDs or purge shared referenced definitions.
9. **P9 — Media forward compatibility.** Version envelope accommodates optional future *stable asset IDs* and format evolution. M5C—not M5B—will decide final file import/size/type/thumbnail, asset ownership, crash safety, storage and garbage collection policy. Never put arbitrary absolute paths in immutable snapshots, rewrite prior snapshots as media arrives, or delete bytes while referenced by any live recipe, draft, history or independently owned record.
10. **P10 — Private notes isolation.** The existing recipe `notes` **content field** belongs in committed content snapshots. The independently versioned M4B-2 private Markdown note, favorites, rating, collection membership and saved filters do **not** belong in M5B committed-content history; preserve their established version/lifecycle behavior. Do not imply encryption.

## Transaction and snapshot contract

- Current verified integration baseline: protected `main` `399f34e4552fc2243331a6e6d398b77b73888b7e`, app 0.1.0, schema 9, Catalog Release 11 (854 canonical / 269 aliases / 50 categories). No M5B code exists at this checkpoint.
- Existing `save_recipe` and `commit_recipe` share Rust `write_recipe`; duplication also calls that write path. Its child row replacement/reinsert approach and the draft closure require a *single* successful transaction to preserve atomicity. Version capture belongs in that transaction **after** the complete validated aggregate is written and **before** COMMIT. Any failure rolls back the entire save, version insert and draft close.
- Use a separate monotonic `version_number` per recipe and a schema-versioned immutable snapshot payload. Snapshot ordered ingredient lines/step IDs, original ingredient IDs, **exact decimal strings** (e.g. `1.250`, without float round-tripping), explicit units and notes, all M5A structured step fields and own-recipe step-to-line links, core recipe data and the recipe's own `notes`. Preserve display-name-at-capture for historical readability without substituting a different ingredient identity. Future extensions must be versioned, not back-edited.
- Require transactional foreign-key / reference preservation for historical ingredient identities even after an ingredient is removed from the active recipe. Retirement is safer than deletion. Historical rendering and restoration are different: an unavailable external/catalog entry can be shown with its captured name/identity, but restore must not silently map it to a different live ID.
- A committed-content fingerprint/canonical comparison must distinguish a no-op from a real content change while preserving original quantity text and user-defined ordering. Make hash/provenance a consistency aid, not a license to skip validation or rewrite history.
- No accidental snapshot for lifecycle-only `recipes.revision` changes. Any future change to independently versioned private notes or organization remains separate.
- Backfill must be idempotent, integrity-checked, bounded for existing libraries and tested with real disposable schema-9 data and legacy fixtures. Do not mutate applied migrations 001–009. Candidate next migration number is 010, **not yet authorized**.

## Reviewable delivery slices (proposed implementation sequence, not coding approval)

| Slice | Scope | Schema expectation |
| --- | --- | --- |
| M5B-1 | Immutable version persistence, safe existing-recipe baseline, transactional capture, exact-text/reference safeguards, lifecycle/rollback tests | Forward-only candidate 010 |
| M5B-2 | Version list and comparison UI, restore-as-new-version, stale/draft handling, Mac native and browser tests | No migration if avoidable |
| M5B-3 | Independent variation creation and symmetric related links, cycle guards, purge constraints | Candidate 011 |
| M5B-4 | Per-line explicit substitutions with optional *user-authored* quantities, historical capture, remove/reorder safety | Candidate 012 |

Each slice requires separate implementation approval, scoped reviewable PR, exact-head five-job CI, isolated Mac GUI PO acceptance where applicable, and independent explicit merge authorization. No migration/PR branch for implementation, release, milestone tag, normal-profile test or data operation was approved by this policy decision.

## Open engineering design work (within the approved behavior)

Precise SQL DDL, historical-ingredient FK modeling under purge, serialization limits and canonical fingerprint design, restore conflict UX, no-op criteria, relation concurrency/uniqueness, and substitution cardinality remain design tasks subject to independent engineering review. Media physical lifecycle/file limits and release/backup guarantees remain for M5C/M9 and later PO gates. Material deviations from P1–P10 require a new explicit PO decision.
