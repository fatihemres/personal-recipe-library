# M4B-1 Recipe Organization — candidate acceptance record

Date: 2026-10-23. Scope: recipe favorites, independent To Try, nullable 1–5 whole-star rating, custom collections and many-to-many membership. M4B-2 owns private/rich notes, saved filters and the real dashboard. This is an engineering candidate, not Product Owner acceptance or merge approval.

## Storage and compatibility

Checksummed migration 007 backfills one organization row for every existing recipe and creates one for each future recipe. Organization has its own optimistic revision. Favorite/To Try/rating changes do not alter recipe content/draft revisions or exact decimal-text quantities. Collection memberships use FKs and composite uniqueness; collection deletion removes its memberships while retaining recipes. Archive/trash preserve metadata; active collection counts exclude both. Purge cascades only the purged recipe's organization and membership rows. The pre-migration online snapshot mechanism remains in place; schema-6 binaries cannot open schema 7 without restoring a compatible backup.

The isolated Rust migration test opens schema 6 containing a recipe with exact `1.250 g`, a recoverable edit draft and Catalog Release 11 with 854 canonical ingredients. It upgrades to schema 7, reopens, validates the migration checksum ledger, draft and quantity, catalog count and `PRAGMA integrity_check`. Separate tests cover FK integrity, stale revisions, Turkish-normalized collection names, no-op toggles, rollback on a failing membership trigger, archive/trash/restore/purge, and organization filters composed with FTS/type/ingredient/date/sort/pagination. No normal user database was opened.

## Safe installation for Product Owner macOS testing

The downloadable PR arm64 package retains Tauri identifier **`com.recipeatlas.desktop`**. The temporary `com.recipeatlas.m4b1verification` identifier was used only for the developer's local isolated smoke build. **Do not open the PR package while signed in to the PO's normal macOS account:** even a bundle kept in Downloads can open and upgrade that account's existing `~/Library/Application Support/com.recipeatlas.desktop/library.sqlite3` to schema 7. An older app cannot safely reopen that upgraded database.

1. Create a disposable **Standard** macOS user in System Settings → Users & Groups, then sign out of the normal account and sign in to the test account. macOS gives that account a separate home directory and application-data profile. Do not copy or point it at the normal account's database, backups or media.
2. In the test account, download `unsigned-macos-arm64` from the latest successful five-job [PR #8 Actions run](https://github.com/fatihemres/personal-recipe-library/pull/8/checks) corresponding to the PR's current head. Expand the downloaded GitHub artifact ZIP in that account's Downloads folder. From the extracted artifact folder, run `shasum -a 256 -c SHA256SUMS.txt`; both `recipe-library-macos-arm64.app.zip` and the DMG must report `OK`. The artifact is unsigned/ad-hoc signed, not a public trusted release.
3. Extract `recipe-library-macos-arm64.app.zip` within the test account (for example, `ditto -xk recipe-library-macos-arm64.app.zip .` in the extracted artifact folder). Open `personal-recipe-library.app` from that test account only; if macOS blocks the unsigned app, use Finder's Control-click → Open or the test account's Privacy & Security “Open Anyway” control. Do not install it into a shared `/Applications` location or weaken security settings in the normal account.
4. Confirm startup, then perform the checklist below with **disposable recipes and drafts created in the test account**. Fully quit and relaunch there. Its own `~/Library/Application Support/com.recipeatlas.desktop/` may be created or upgraded; the normal account's profile stays separate. A clean test account cannot prove migration of the PO's existing personal recipes; the automated isolated schema-6→7 test covers that path. Any later real-profile upgrade requires a separately verified backup and explicit PO decision.

## Product Owner Mac acceptance checklist

1. Use the disposable Standard account and verify the **current-head** arm64 artifact checksums as described above; never launch this package in the normal PO account during candidate testing.
2. Launch in the test account; confirm no storage/catalog error and Catalog Release 11 remains searchable. Create a disposable recipe and edit draft with an exact decimal quantity such as `1.250 g` for the relaunch check.
3. Favorite a recipe from card and list views, toggle To Try independently, then filter active recipes by each and both together.
4. Open detail; set, change and clear a 1–5 rating using keyboard and mouse. Confirm no rating is shown as unrated rather than zero.
5. Create two collections, add one recipe to both, rename one, and verify counts and membership. Delete a collection and confirm the recipe remains.
6. Archive, trash and restore an organized recipe; confirm active views hide it appropriately and restoration retains organization. Test confirmed permanent purge only with a disposable recipe.
7. Fully quit and relaunch in the test account. Check flags, rating, collections, recipe content, drafts and exact decimal quantity/unit remain intact. The normal account's personal data must remain unopened throughout this candidate test.

Do not merge or tag until the PO explicitly accepts this build and separately authorizes the exact PR head for a merge commit.
