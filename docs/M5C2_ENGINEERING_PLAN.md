# M5C-2 — single optional recipe-step photo: engineering design proposal

**As of 2026-11-05: PROPOSED TECHNICAL DESIGN / NO CODING AUTHORIZATION.** This document describes a reviewable approach to the already PO-approved product constraints in [DEC-037](../DECISIONS.md) and [Issue #36](https://github.com/fatihemres/personal-recipe-library/issues/36#issuecomment-6654574878). The PO approved **scope and image privacy rules**, not the proposed SQL, snapshot format or API shape. Any coding, new migration, implementation PR merge, tag, release, or access to ordinary user data requires separate authority.

## Verified baseline, dependency and scope

- Protected `main` at planning discovery: `6fca8e2aafef0de24caa42138bd715b470851b3f`. M5C-1 cover/media is **INTEGRATED + scoped PO_ACCEPTED**, schema **13**, content-history format **3**, Catalog Release **11** (854 canonical, 269 aliases, 50 categories), app **0.1.0**.
- `src-tauri/src/media/mod.rs` validates, bounds, sanitizes and journals immutable media. Existing Rust-only picker, safe `recipe-media` thumb/preview serving, one-import gate, UUID-relative paths and explicit lack of physical GC are the starting point. Reuse the media foundation without granting renderer generic FS/SQL/network access.
- `RecipeStep` is keyed by stable UUID; `src/features/recipes/RecipeSteps.tsx` already reorders by step identity. `persistence/recipes.rs` currently deletes/reinserts step rows within the recipe transaction; `reliability.rs` persists draft JSON under CAS and pins the single cover in `draft_media`; history formats 1/2/3 are independently validated and immutable.
- M5C-2 delivers **0 or 1** optional photo per step. Previous suggestions of **4** per step, multiple images, photo ordering, thumbnail galleries or a new cover gallery are **superseded**. Reordering recipe steps retains the photo bound to the step UUID.
- **PO-approved image constraints:** local static JPEG/PNG/WebP only; **20,000,000 bytes per selected input**, **30,000,000 decoded pixels**; reject HEIC/HEIF and corrupt/animated/resource-exhausting inputs; source file is never modified; app-owned import copy strips EXIF/GPS while maintaining display orientation/transparency within existing M5C-1 codec limitations. No URLs, online fetches, mandatory video, sync, arbitrary file browser access, metadata retention or unlicensed bundled photos.

## Proposed contract and experience (requires engineering acceptance)

- Add one optional `photoAssetId?: string | null` (strict UUID) to the existing typed `RecipeStep` in Rust, TS/Zod, IPC, persisted drafts and new history. Absent/null both represent no photo at the input layer; choose a **canonical serialized representation** for new-format snapshots, without changing bytes of formats 1–3.
- Inside each existing step's compact advanced editor section, show an on-demand **Fotoğraf ekle** action; after import, show one lazy thumb/preview and replace/remove controls. The main editor stays usable with no images. Provide accessible Turkish labels, keyboard/focus handling and retry on missing previews. A step's photo remains with it when steps reorder.
- The **PO-required explicit confirmation** fires *before deleting any step that currently has a photo*, including a newly imported draft photo. Cancel leaves step and asset association intact. Confirm removes the step **from the draft only**; persisted recipe remains untouched until deliberate Save. Failure or Cancel of the native picker changes no draft. Replace/remove-photo UX can remain an ordinary draft change; any additional confirmation for those actions would be a separate UX recommendation, not a PO policy.
- Save/no-op/Discard/Save As New and acknowledged Cmd-Q/durable-draft behavior remain unchanged. Photo import itself may create an immutable app asset; abandoning it is safe but does not physically GC it under the existing conservative policy.
- Detail view shows the photo beneath its associated step; historical step preview/compare shows the photo belonging to that captured step/version. Old snapshots lack step images. Duplicate and Variation create independent recipe/step IDs and histories, optionally **sharing immutable asset bytes/UUIDs**, never shared mutable step associations.

## Proposed data model — candidate additive migration 014 / schema 14

**No existing applied migration may change.** Design and verify a new checksummed, forward-only `014_recipe_step_media.sql`; do not assume DDL below is pre-approved. Avoid overloading the existing **single-cover** `recipe_covers`, `draft_media`, or `recipe_version_media`.

| Candidate table | Proposed key/ownership | Important invariants |
| --- | --- | --- |
| `recipe_step_media` | `PRIMARY KEY(recipe_id,step_id)`; composite FK `(recipe_id,step_id)` → `recipe_steps(recipe_id,id)` | At most one ready `media_assets.id` per real owned step, CAS recipe save, cascade association only on step deletion, never physical asset deletion |
| `draft_step_media` | `PRIMARY KEY(draft_id,step_id)`; FK to active `editor_drafts` plus ready asset | Draft step UUID must exist exactly once in validated draft JSON; update pin rows in the same draft-CAS transaction and close/discard ownership safely |
| `recipe_version_step_media` | `PRIMARY KEY(recipe_id,version_number,step_id)`; FK to immutable `recipe_versions` and ready asset | Snapshot-derived reference pin matches exact step/photo UUID for new format 4, immutable except owned version/recipe purge; older format 1/2/3 never gain photos |

Indexes by `asset_id` are needed for future reference enumeration, but **do not introduce physical media GC**. Require schema/triggers/service checks for ready-only assets, cross-recipe step IDs, duplicate UUIDs, bad or missing step references, immutable version pins and failed transactions. Since draft-only steps are not rows in `recipe_steps`, `draft_step_media` cannot use a `recipe_steps` FK; app-side validation must cross-check each pin with the validated draft JSON, preferably with a database-enforced consistency guard where practical.

**Critical writer ordering:** existing recipe writer **DELETEs `recipe_steps` and re-INSERTs them**. In the same IMMEDIATE recipe CAS transaction, validate each step photo UUID, recreate child step rows, reattach 0/1 photo associations for the submitted stable step UUIDs, and *then* capture the immutable recipe version. A failure must rollback all content, cover, photo associations and history together; not lose photos through child-row cascade or leave a window of unpinned ready assets. Reads should batch step/photo associations per recipe to avoid N+1 image lookups. Never leak source paths into SQL/DTO/snapshots.

## Proposed history format 4, preserving formats 1–3

- **Formats 1, 2 and 3 bytes, checksums and format-specific fingerprint projections are frozen.** The current Rust `comparison_v1/v2/v3`, existing SQL ledger and immutable snapshot payloads must not change. Extend the format-aware dispatcher to **4** and add a dedicated comparison_v4 that includes each step's `photoAssetId` alongside all existing content. Do not merely reinterpret historical format 3 as if it contained photos.
- New captures may use format 4 and reference UUIDs, not source paths or binary image bytes. Compare actual content across old/new formats so an unchanged Save or upgrade alone cannot create a spurious content version. For a historical format 1/2/3, the *step photo state is empty*; restoring creates a **new format-4 history entry** only when content actually differs, and never mutates historical serialized records.
- Immutable version pin rows should be derived/validated from each format-4 snapshot's step/photo associations; a missing or non-ready asset must produce a recoverable error, not erase history. Keep ingredient alternative reference projections and cover reference validation intact; `check_purge_format`, future-version refusal and source deletion safety must explicitly support format 4 before migration is shipped.
- **Migration 014 should not backfill or rewrite old snapshots**. A normal pre-upgrade SQLite online snapshot is *not* a portable media backup. Document downgrade limitations and idempotent fail/retry behavior.

### Forward-only schema-14 SQL trigger compatibility gate

- **Existing migration-013 trigger gap, verified in integrated source:** `media_history_capture` derives `recipe_version_media` cover pins only for history format **3**, and `media_history_insert` validates pins only against format 3. `version3_alternatives_capture` derives alternative pins only for format 3; `version_alternatives_validate_insert` validates alternatives only for formats **2 or 3** (migration 012 separately captures format 2). A new format-4 snapshot containing a cover and ingredient alternatives would therefore be incompletely pinned if migration 014 added *only* step-photo tables.
- In the **new additive, checksummed migration 014 only**, design replacement/extension of the affected SQL trigger definitions so both **format 3 and format 4** cover history and **format 2/3/4** ingredient-alternative history remain fully captured and referentially validated. Do **not** edit applied migration SQL 001–013 or mutate existing history rows, checksums, captured pin rows, or format-specific fingerprint projections. Preserve historical capture behavior for all older formats.
- Derive each format-4 step-photo pin from its own immutable snapshot and validate the exact `(recipe_id, version_number, step_id, asset_id)` pairing and ready asset. Review the insertion sequence of `recipe_versions` and dependent triggers for atomic rollback: rejecting any cover, alternative, or step-photo pin must abort the entire recipe Save/CAS/history transaction, not create a partial snapshot. Historical pins must remain immutable except during an explicitly owned, reviewed purge.
- Required isolated SQLite proof: existing format-2 alternatives, existing format-3 **cover plus alternatives**, new format-4 **cover plus alternatives plus optional step photos**, old-format restore as new format 4, same-content Save/no-op across formats, invalid/not-ready assets, tampered references, shared-asset Duplicate/Variation, and permanent target-only purge. Verify snapshot/ledger byte identity for formats 1–3 and FK/integrity results before and after schema13→14 upgrade. Do not infer correctness from a documentation-only PR or browser mocks.

## Safe media reference lifecycle and availability

- Archive/Trash/restore preserve 1:1 step associations and immutable assets. A reviewed permanent purge removes only owned recipe/draft/version links, with SQLite integrity controls; any asset referenced by other live recipes, drafts or historical versions survives. In the current conservative policy, **all finalized assets remain physically retained even after their last reference is removed**. Be explicit about disk growth.
- Missing/corrupt stored media yields visible recoverable UI state and safe retry/repair of derivatives; never silently NULL photo IDs or rewrite old snapshots. The import staging/finalize/SQLite journal and startup recovery from M5C-1 remain authoritative.
- M9 must ultimately export one coherent SQLite snapshot **plus all referenced assets/manifests and integrity hashes**. M5C-2 **does not implement full portable backup/restore**, disk GC, cloud or sync.

## Minimum test/QA gates before any milestone claim

1. **SQLite:** fresh schema-14 and isolated schema-13→14 upgrade; exact immutable migration 001–013/ledger and Catalog11 checks, integrity/FKs, failed migration/retry, old history 1–3 bytes/checksums/fingerprints unchanged.
2. **Atomicity and data:** 0/1 step image validation, invalid UUID/asset/not-ready/missing step/cross-recipe reference rejection; reorder steps without remapping photo to the wrong step; delete step confirmation+cancel, duplicate/variation ID remapping with safe shared bytes, archive/Trash/restore/reviewed purge, history v4 capture/compare/no-op/restore, draft recovery and restore from pre-photo versions.
3. **Media:** actual valid static JPEG/PNG/WebP (including orientation/transparency/Turkish filename), HEIC/animated/corrupt/spoofed/oversized rejection, picker cancel, offline/network denied, staged crash/reconcile, safe missing-file/thumbnail handling, protection of old cover import and historical references.
4. **UI:** browser/React test matrix at 520/640/768/1024/1440/1920 CSS px in light/dark, keyboard/a11y/focus, long Turkish text and no overflow, no silent delete of photo-bearing steps, lazy thumbnails rather than full-res decoding per step. A mocked IPC browser test is **not** native SQLite/filesystem evidence.
5. **Native + release governance:** separately packaged/isolated real Mac acceptance (create/import/save/relaunch, confirmed/cancelled step deletion, reorder, duplicate/variation, old/new history restore, archive/Trash/reviewed purge); explicit evidence limits for Windows/Intel real GUI and daily-profile upgrade; independent security/QA review, **five exact-HEAD CI PASS**, distinct PO milestone acceptance and **separate PR merge authorization**.

## Engineering review questions / blockers before code

- Confirm whether the proposed schema-14 ownership and history-4 representation cleanly enforce **one asset per stable step** without requiring an extra mutable side channel.
- Prove that snapshot format 1–3 deserialization and fingerprints are byte-identical and that format-4 restore/no-op semantics do not create false versions, especially for pre-photo snapshots.
- Confirm draft pin rows stay synchronized with autosave/CAS and cannot drop references upon Save As New, duplicate, deletion, or a crash.
- Verify the practical maximum number of step photos per recipe (up to existing 500 steps) has **no additional PO-approved total limit**. Quantify memory, thumbnail requests, storage and UI virtualization; propose a new explicit cap only with separate PO policy review if needed.
- Treat existing pre-M5C-2 [ingredient-alternatives Playwright geometry flake](https://github.com/fatihemres/personal-recipe-library/actions/runs/41999294277) as a separate quality follow-up, not a reason to relax assertions silently.
- Submit a scoped M5C-2 coding brief for a **separate explicit PO coding authorization**. Do not treat this technical document or its PR as approval to write code.

**Out of scope:** multi-photo step galleries/order, multiple covers, HEIC/HEIF, remote photos, unlicensed catalog images, AI imagery, video, M5D Cooking Mode, automatic physical asset GC, M9 complete backup/restore, production-profile migration, tags and releases.
