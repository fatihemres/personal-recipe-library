## Delivered contract

- One immutable V1 for new food/beverage recipes; one next version for each meaningful committed-content change. Version numbering is independent of `recipes.revision`. No-op Save appends nothing, while preserving the established recipe revision increment, timestamp update and draft-close behavior. No automatic pruning.
- Core content includes recipe `notes`, ordered ingredient **line IDs**, ingredient IDs, exact quantity text (`1.250` stays distinct from `1.25`), units, nullable notes and captured display labels; ordered M5A steps include metadata and same-recipe line links. Snapshots retain old labels after live ingredient renames.
- Canonical comparison uses an explicit frozen V1 projection with recursively sorted keys. Input is the fully persisted aggregate after existing trimming/duration normalization. Exact strings/NULLs and line/step order matter; association order is a set. Empty metadata-only wrappers equal absent details. Labels, creation/capture timestamps, lifecycle and CAS counters do not affect equality. An independently generated golden fingerprint pins the algorithm. A separate full-payload SHA-256 protects all stored bytes, including labels.
- Private Markdown notes, favorites, To Try, rating, memberships and saved filters are independent. Archive/trash/restore-from-trash retain history and generate no content versions. Draft autosave/discard/recovery does not generate snapshots. Duplicate and explicit Save As New remap IDs and receive their own V1, not a copied version chain.
- No history/compare UI, restore command, variations, related recipes, substitutions, media management, Cooking Mode, conversions, preparation logging or backup/export feature is delivered.

## Storage, upgrade and references

Forward-only `010_recipe_versions.sql` SHA-256: `502dc88c0913bc2276d9bb4f42908d54b541841111e8f2d97f0e2c06e47515b4`. Migrations 001–009 are unchanged. `recipe_versions` owns versioned, bounded JSON (128 MiB ceiling accommodates current aggregate limits), positive monotonic numbers, source CAS revision, timestamp, provenance, comparison hash and full checksum. `created`/`upgrade_baseline` are V1-only; later ordinary captures use `edited`. `restored` and its same-recipe prior-version FK are reserved for later implementation, not a restore command.

The common `write_recipe` captures **after** all authoritative rows/search writes and **before** its existing transaction commits. `save_recipe`, `commit_recipe` plus draft closure, and `duplicate_recipe` share this hook. Snapshot insertion/readback or draft-close failure rolls back the entire operation. Stale competing saves cannot append phantom versions. Failed/unsupported payloads are never silently narrowed into a valid current recipe.

Migration 010's Rust backfill hook runs within the existing migration IMMEDIATE transaction, after the existing online pre-migration snapshot and before ledger/user_version commit. It pages 64 recipe IDs and loads one aggregate at a time. Every existing active, archived and trashed recipe gets one honest `upgrade_baseline`, recording current persisted data and actual capture time, not invented earlier edits. Counts and migration FK/integrity checks precede commit. Failed or killed uncommitted backfill leaves the complete original schema-9 database; restart retries from that valid state. Normal opens do not scan/rebuild all history or rerun baseline capture. Malformed historical aggregates stop the upgrade without silent repair; the original profile and backup remain for explicit investigation.

SQL triggers block version UPDATE, per-version DELETE and replacement bypasses; numbering is checked at insert. Reference rows are derived from the payload in the same INSERT, with restrictive ingredient/unit FKs. A removed current line does not release its historical definitions. Renaming never remaps ingredient identity. The existing explicit trash/revision-checked recipe purge cascades **owned** versions and refs only; shared definitions, other recipes and orphan edit drafts remain independently protected. No per-version deletion/pruning API exists. Turkish errors explain historical-reference protection; the existing irreversible purge confirmation explicitly discloses deletion of retained content versions.

Format dispatch checks the header before strict V1 parsing. A later format may add stable media asset IDs without rewriting V1 bytes. This build refuses Save and permanent purge when retained history uses an unsupported format (`RECIPE_VERSION_UNSUPPORTED`), rather than losing unknown references. Future media schema/physical lifecycle is not implemented. Internal metadata reads use keyset pagination (1–100); full payloads are read singly and validated/checksummed. No history IPC is exposed yet.

An older schema-9 binary must not open schema 10. Git rollback does not undo migrations or user changes. Restore a separately preserved, compatible pre-upgrade backup only with an explicit recovery plan accepting loss of newer edits. The internal online snapshot is not M9 portable backup/export.
